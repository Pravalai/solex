soleX Round 2 · architecture

How soleX OS fits together

One app, one database and one set of business rules serve five kinds of user. A partner's registration becomes the lead, the booking changes the inventory, and the money collected releases the commission. Each step happens once, in one transaction, and every screen reads the result.

01Layers: from a person to the database

Every screen, for every role, goes through the same path. The browser never talks to the database, and no screen has its own copy of the rules.

02Module dependencies

Which part of the system calls which. Arrows point from the caller to the module it depends on. There are no loops, so each module can be changed and tested on its own.

03Lead to commission, end to end

The demo's main journey. Each column is one step, done by one person; the bottom row lists what the system changes in that same step. The gold tags show the mandate rule each step obeys.

04Data model: the mandate at the centre

soleX is not a broker. Its unit of business is the mandate, the contract with a developer, so every unit, booking and commission line points back to one.

05Linked status changes

Lead, unit, booking and commission each have a fixed set of allowed moves. The events across the top move all four at once, in a single transaction, so they can never fall out of step.

06Why a unit cannot be sold twice

Two execs click "Book" on the same unit in the same second. Both were looking at version 7 of it. Only one can win, and the loser's attempt leaves no trace.

Working in the demo

  • Sign-in, roles, permissions and data separation
  • Leads, attribution, duplicate blocking, visits
  • Holds, bookings, two-level approvals, cancellations
  • Schedules, receipts, the 20% trigger, the commission ledger
  • Command centre, partner and developer portals, CSV export
  • Audit trail and live integrity checks

Simulated, by design

  • WhatsApp, email and SMS: written to an outbox, never sent
  • Payment gateway: finance types in the receipt
  • Accounting and ERP posting, GST and TDS
  • Partner brochure downloads

Why one app, not many services

  • A booking must change four modules together; one database transaction does that simply
  • One deployment and one team to run it
  • Module boundaries are already clean, so messaging, reporting or integrations can move out later without a rewrite
